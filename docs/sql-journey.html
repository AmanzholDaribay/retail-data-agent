What happens to the AI's SQL on its way to BigQuery?

It passes through four steps in one file, gateway.py. Some steps only check the SQL. Two of them rewrite it, so what BigQuery runs is safer than what the AI wrote. Below, one real question goes all the way through. See also every parser rule, brand scoping and the agent loop.

the AI a check: only reads the SQL a rewrite: changes the SQL BigQuery stopped here

In short

  1. Checks first. Is it a safe, single read of our 4 tables, using only allowed columns? If not, it stops, and the AI gets the reason so it can fix its SQL.
  2. Then two rewrites. Customer ids become nicknames like cust_249e6e6fc97d, and every table is cut down to the user's brands.
  3. Then a free size check. Anything that would scan more than 1 GB is stopped before it costs money.
  4. Only then BigQuery runs it. The rows go back to the AI, which writes the answer.

One question, step by step

“Who are my top 3 customers?”
asked by the Levi's manager (--user levis_manager), who may see Levi's only
The AI writes SQLLLM → run_sql tool

It writes the obvious query over the real tables. No brand filter, no nicknames: it doesn't have to think about safety.

SELECT u.id, u.country, COUNT(DISTINCT o.order_id) AS orders
FROM `…thelook_ecommerce.users` u
JOIN `…thelook_ecommerce.orders` o ON o.user_id = u.id

ORDER BY orders DESC

Step 2b · Customer pseudonymsstep2_personal_data/customer_pseudonyms.py

The customer tables are swapped for copies where each real id is replaced by a nickname. BigQuery makes the copies itself while it runs, so the AI's part of the query only ever sees nicknames. This happens for every user, the CEO too.

🏠 Like a coat check: you get ticket #72, never the hanger's location. Same coat, same ticket, every time.

WITH _pseudonymized_users AS (
  SELECT * REPLACE (CONCAT('cust_', …SHA256(@pseudonym_salt + id)…) AS id)  -- 48213 → cust_249e6e6fc97d
  FROM `…users` AS users),
_pseudonymized_orders AS ( …same for user_id… )
SELECT u.id, u.country, COUNT(DISTINCT o.order_id) AS orders
FROM _pseudonymized_users AS u
JOIN _pseudonymized_orders AS o ON o.user_id = u.id   -- nickname = nickname, so the join still matches
GROUP BY u.id, u.country ORDER BY orders DESC LIMIT 3
Step 3 · Brand scopestep3_brand_scope/brand_scope.py

Every real table, including the ones inside the nickname copies, is swapped for a copy that holds only Levi's rows. Customers and orders are kept only if they bought a Levi's product. The CEO sees every brand, so this step skips the CEO.

🏠 Like handing someone a filing cabinet that holds only their own folders.

WITH _brand_scoped_products AS (… WHERE brand IN ('Levi\'s')),
     _brand_scoped_order_items AS (… only Levi's products …),
     _brand_scoped_orders AS (… only orders with a Levi's item …),
     _brand_scoped_users  AS (… only people who bought Levi's …),
     _pseudonymized_users  AS (… FROM _brand_scoped_users …),
     _pseudonymized_orders AS (… FROM _brand_scoped_orders …)
SELECT … FROM _pseudonymized_users AS u JOIN _pseudonymized_orders AS o …
✕ Stopped if a table has no brand rule → Table … can't be limited to your brands, so the query was not run.

The AI answersLLM

It reads the three rows and writes the answer in plain words. If the user follows up with “what did the first one buy?”, the AI writes WHERE user_id = 'cust_249e6e6fc97d', and the whole journey runs again: the copies are rebuilt the same way, so the nickname matches.

What stops a query, and what the AI is told

A stopped query never reaches BigQuery. The AI gets the message as Error: …, fixes its SQL and tries again, within its 5 LLM calls per question.

Steps 2b and 3 never stop a normal query and never tell the AI anything: they quietly rewrite it.

The rule in one sentence

The AI writes plain SQL, the gateway checks it, then rewrites it for privacy and brands, and only that rewritten SQL reaches BigQuery.
