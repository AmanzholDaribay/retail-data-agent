Retail data agent · How one question runs

The agent loop, as a circle

Each question goes round this circle until the model answers. The database work happens outside the circle: the tool hands SQL to the gateway, the gateway to BigQuery, and the result comes back in.

middleware (CallBudget, ModelFallback) LLM tool and data path end of the question
  1. before_model: CallBudget checks the count. Under 5, the loop goes on. If the 5th call still asked for SQL, it jumps to END with "I couldn't finish this question…". That is only a fallback: normally the 5th call answers.
  2. LLM call: the model either writes SQL (a tool call) or gives the final answer. It sees the earlier turns of the conversation too, so follow-up questions work. On the 5th call CallBudget removes the tools and adds a note: answer now from the results you have, and say what is missing. If the call fails (out of quota, busy, timed out), ModelFallback sends the same request to the next Gemini model, which gets the same tools and the same last-call rule. The switch doesn't count as an extra call; see docs/model-switching.html.
  3. after_model: CallBudget adds 1 to the count. With no tool calls, the answer goes to END. With tool calls, the loop goes on.
  4. run_sql tool: hands the SQL out of the circle to the QueryGateway. The guard checks it is one SELECT over the 4 tables, a dry-run checks it stays under the byte limit, and only then does it run in BigQuery.
  5. tool result: the rows come back into the circle as a table (with a note if rows were cut off or none matched), or Error: … if the gateway or BigQuery rejected the query, and the loop returns to before_model.
Code: agent.py (CallBudget, ModelFallback, the loop via create_agent), tools.py (run_sql), gateway.py, guard.py, db/bigquery.py; the conversation is kept in app.py. See also docs/middleware.html, docs/model-switching.html and docs/sql-errors.html.
