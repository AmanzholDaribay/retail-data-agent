Retail data agent · Brand scoping · as of 2026-10-31

How does a brand manager see only their own brands?

The AI writes SQL as if it could see every brand. Before that SQL runs, our code swaps every table in it for a smaller table that holds only the user's brands. The AI can ask for anything, but other brands' rows are simply not there. See also one query's full journey, the architecture and what happens when a query fails.

What the AI wrote Filtered to the user's brands BigQuery Stopped

In short

  1. The user is picked at startup (--user levis_manager), and users.yaml says which brands they see. The CEO has all.
  2. The filter is applied by code to every query, not checked for and not asked of the AI, so no prompt can talk its way around it.
  3. Only products has a brand. The other tables are filtered through the IDs that link them to those products.

Where the filter sits

1 · The AI writes SQL

Plain SQL over the four real tables. It doesn't need to filter by brand, and no filter it writes can widen what it sees.

2 · Guard and personal data

One SELECT, only the four allowed tables, only the columns in schema.yaml, no *, nothing it can't parse. Then customer ids become pseudonyms such as cust_72ac84091163, for every user. See the parser rules.

✕ anything else is stopped here
3 · Brand scope (new)

Swaps each table for its brand-filtered version, including the real tables inside the pseudonym copies, so a manager's pseudonyms come from their own customers only. The CEO skips this step.

4 · Size check

A free dry run of the filtered SQL: over 1 GB is stopped.

5 · BigQuery runs it

The rows that come back belong to the user's brands only.

How each table reaches a brand

Only the product catalog knows brands. Everything else follows the links back to it, the way a receipt leads back to the shop that sold the item.

products
WHERE brand IN ('Levi\'s')

Only the user's brands. This is the root of every other filter.

order_items
product_id IN (those products)

Items sold of those products.

orders
order_id IN (those items' orders)

Orders with at least one such item.

users
id IN (those items' buyers)

Customers who bought at least one.

A real example: levis_manager counts products

The AI writes the obvious query, with no brand filter at all:

SELECT brand, COUNT(*) AS n
FROM `bigquery-public-data.thelook_ecommerce.products`
GROUP BY brand

The brand scope adds the four filtered tables at the front and points the query at them. The AI's own part is unchanged:

WITH _brand_scoped_products AS (
  SELECT * FROM `bigquery-public-data.thelook_ecommerce.products` AS products
  WHERE brand IN ('Levi\'s')),           -- built by our code, from users.yaml
  _brand_scoped_order_items AS (…),       -- the other three are always added too;
  _brand_scoped_orders AS (…),            -- BigQuery skips the ones a query
  _brand_scoped_users AS (…)              -- doesn't read, at no extra cost
SELECT brand, COUNT(*) AS n
FROM _brand_scoped_products AS products  -- old name kept as alias
GROUP BY brand

BigQuery returns one row: Levi's · 259. For denim_lead (Levi's and Calvin Klein) the same query returns two rows, Calvin Klein · 497 and Levi's · 259. That was checked against the live data on 2026-10-31, and it scanned 0.35 MB.

Two ways to do it, and why we rewrite the SQL

A · Rewrite the SQL · chosen

Our code edits each query before it runs, using the same SQL parser the guard already uses.

  • Nothing to set up: works with any reviewer's key and project.
  • A new user is one line in users.yaml.
  • Fully tested offline, with tricky queries.
  • The rule lives in our code, so only queries that go through the gateway are protected.
B · Scoped views · put aside

Pre-filtered views per user, stored in BigQuery. The gateway only points the query at that user's views.

  • The filter lives in the database, so other tools get it too.
  • In production, each login could read only its own views.
  • Needs datasets and views created in an external service (a GCP project), and kept in step with users.yaml.
  • Can't be tested without live BigQuery, and the gateway still has to swap table names.

For a prototype that reviewers run with their own free key, the setup cost of B decides it. B remains the natural production upgrade: the same four filters, moved into views behind per-user access.

The rule in one sentence

Never ask the AI to respect brands: swap every table it reads for one that already holds only the user's brands, and stop any query where that can't be done.
