How do we stop a total from describing one person?

Columns like age and city are fine in a total over many customers, but a "total" over one customer is really that customer. We tag those columns in schema.yaml. The gateway then allows them only inside totals, and makes BigQuery drop every group with fewer than 5 customers. See also one query's full journey and every parser rule.

config: the tag and the limit the gateway changes the SQL runs as today shown rejected or hidden

In short

  1. Tag the columns. In schema.yaml, age, gender, city, state, country and traffic source get aggregate_only: true.
  2. Listed one row per person? Rejected. The AI is told to use the column only inside a total.
  3. Inside a total? Allowed, and the gateway adds HAVING COUNT(DISTINCT user_id) >= 5, so BigQuery drops the small groups itself.
  4. No tagged column? Nothing changes. "Top customers by spend" still works through pseudonyms.

What "tagging" means

A tag is one extra label next to a column in schema.yaml. The data doesn't change; the label tells the gateway how to treat that column, like a "fragile" sticker on a box. To protect another column, you edit the file, not the code.

Today 
users:
  age:    {type: INT64}
  city:   {type: STRING}
  state:  {type: STRING}
  status: …
With the tag 
users:
  age:    {type: INT64,  aggregate_only: true}
  city:   {type: STRING, aggregate_only: true}
  state:  {type: STRING, aggregate_only: true}
  status: …  # no tag: works as today

Tagged: users age, gender, city, state, country, traffic_source, plus orders.gender, which is the same fact copied onto every order.

Example: "average age of Levi's buyers in each city"

  1. The AI writes a total, which is the allowed kind:
SELECT u.city, AVG(u.age) AS avg_age
FROM users u JOIN order_items oi ON oi.user_id = u.id
GROUP BY u.city
  1. The gateway sees the tagged city and age inside a total, so it adds one line:
SELECT u.city, AVG(u.age) AS avg_age
FROM users u JOIN order_items oi ON oi.user_id = u.id
GROUP BY u.city
HAVING COUNT(DISTINCT u.id) >= 5   # 5 = MIN_GROUP_SIZE in .env
  1. BigQuery counts the customers in each city and leaves out the small ones before sending anything back:

Three queries, three outcomes

Listing a tagged column 
SELECT id, city, age
FROM users

❌ Rejected. One row per person would show each customer's city and age.

A total of a tagged column 
SELECT country, SUM(…)
… GROUP BY country

✅ Runs with HAVING ≥ 5 added. Countries with 1–4 customers are left out.

No tagged column 
SELECT user_id, SUM(…)
… GROUP BY user_id

✅ Unchanged. Each row is one customer, but only as a pseudonym like cust_72ac84091163.

ARRAY_AGG and STRING_AGG are rejected in these totals: they return one row per group, but it still holds every customer's value. Why HAVING and not dropping rows in Python afterwards: SQL applies HAVING before LIMIT, so "top 3 countries" still returns 3 safe rows instead of 3 rows minus the hidden ones.

What it doesn't stop

Subtracting two totals

"Total spend, all countries" minus "total spend, all countries except Iceland" gives Iceland's one customer. Each query passes on its own. Real protection needs added noise (differential privacy), which is beyond this prototype, so the design doc names it as a known limit.

The rule in one sentence

A tagged column can reach the AI only inside a total, and only when that total covers at least 5 customers, counted and enforced by BigQuery itself.
