Retail Data Agent Map

How one question travels from your terminal to BigQuery and back, and why each file in the repo exists. See also why run_sql has a factory, how each user sees only their brands, and how the parser rules stop a bad query.

One question, end to end

Each box is a file. The agent and the LLM go back and forth until the model has enough data to answer. A normal question takes 2 LLM calls.

cli.py

Started as retail-agent --user levis_manager; the user and their brands come from users.yaml (users.py). You type "Top 5 brands by revenue last month?". Prints the SQL and ANSWER blocks, or a clear message if the model is busy.

app.ask(question)
app.py → App.ask

Sends the question to the agent and collects the answer plus every SQL statement run during the turn. Keeps the conversation under one thread id, so follow-up questions see the earlier turns.

invoke

The agent loop

  1. LLM reads the question, the earlier turns, the schema and the rules, then writes SQL.
  2. run_sql runs it and returns rows as a table.
  3. LLM reads the rows and writes the answer.

If the SQL fails or the guard rejects it, the error goes back to the LLM so it can fix it. A question gets at most 5 LLM calls; the 5th has no tools, so it answers from the results it already has.

agent.py

LangChain create_agent: the loop between the model and the tool, with CallBudget middleware for the 5-call limit and a checkpointer that saves the conversation.

model ⇄ tool
llm.py

Builds the chat model from LLM_PROVIDER:LLM_MODEL, with a 30 s timeout and 1 retry. Gemini by default; Claude when you switch it on.

tool call: run_sql(sql)
tools.py → run_sql

The only tool. Hands the SQL to the gateway and turns the result into a compact text table for the LLM (result_format.py), with a note when rows were cut off or none matched. A rejected query comes back as Error: ….

gateway.run(sql)
query_safety/gateway.py → QueryGateway

The only path to the data. Logs the SQL, runs the guard (query_safety/step1_guard.py: one SELECT, only the 4 tables), lets the query read only the columns in schema.yaml so no personal data gets out (query_safety/step2_personal_data/columns.py), shows customer ids only as pseudonyms such as cust_72ac84091163 (query_safety/step2_personal_data/customer_pseudonyms.py), limits it to the user's brands (query_safety/step3_brand_scope/brand_scope.py), rejects a query whose dry-run estimate is over the byte limit, caps rows. See one query's full journey, the parser rules and brand scoping.

database.execute(sql, max_rows)
db/bigquery.py

Runs the query in BigQuery, billed to GCP_PROJECT, never more than MAX_BYTES_BILLED. Follows the Database protocol in db/base.py.

job
bigquery-public-data.thelook_ecommerce

orders · order_items · products · users. A typical question scans 3–7 MB.

What you see in the terminal for that question:

> What were the top 5 brands by revenue last month?
Working...

── SQL ─────────────────────────────────────
SELECT p.brand, ROUND(SUM(oi.sale_price), 2) AS revenue
FROM `bigquery-public-data.thelook_ecommerce.order_items` AS oi
JOIN `bigquery-public-data.thelook_ecommerce.products` AS p ON oi.product_id = p.id
WHERE oi.status NOT IN ('Cancelled', 'Returned')
  AND oi.created_at >= TIMESTAMP(DATE_SUB(DATE_TRUNC(CURRENT_DATE(), MONTH), INTERVAL 1 MONTH))
  AND oi.created_at < TIMESTAMP(DATE_TRUNC(CURRENT_DATE(), MONTH))
GROUP BY p.brand ORDER BY revenue DESC LIMIT 5

── ANSWER ──────────────────────────────────
1. Diesel: $8,024.59      2. True Religion: $7,671.26
3. Calvin Klein: $7,036.47   4. Carhartt: $6,073.56   5. 7 For All Mankind: $6,024.97
Revenue = sum of sale_price, excluding Cancelled and Returned items.

Meanwhile observability.py and query_safety/gateway.py write each step to logs/retail-agent.log: each LLM call with its duration, each SQL with rows and bytes.

At startup, once

Before the first question, app.py puts the pieces together. build_app creates the real model and database; assemble wires them. Tests call assemble directly with fakes.

.env → config.py

Model, keys, GCP project, row and byte limits. .env is never committed.

schema.yaml → schema.py

The 4 tables, cleaned up, with short notes. Names, emails and addresses are left out on purpose.

prompts/system.md

The rules: answer only from query results, compute dates in SQL, state the revenue definition.

system prompt

Rules + schema + SQL dialect, sent with every LLM call. The agent never has to look up the schema itself.

Where later steps plug in

The structure exists so each step adds to one place instead of rewriting the rest.

Query gateway

  • Done in step 2: only single SELECTs on the 4 tables; dry-run byte check
  • Done in step 3: every query limited to the user's brands
  • Done in step 3: only schema.yaml columns, no *, so no personal data
  • Done in step 3: customer ids only as salted-hash pseudonyms, for every user
  • Step 3 next: demographics only in totals, groups under 5 hidden

Agent middleware

  • Done: at most 5 LLM calls per question, the last one answers
  • Step 5: confirm before deleting reports

Database protocol

  • Ticket 05: check schema.yaml against live tables at startup
  • Another engine = another adapter, nothing else changes

Tests via assemble

  • Fake LLM records exactly what it was sent
  • Step 3 uses this to prove personal columns never reach the database or the LLM
