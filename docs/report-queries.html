One Report Question, Several SQL Queries

How the agent should answer report questions such as “create a Q1 report with action items for Q2”: send several SQL queries at once, run them at the same time, then write the report. Confirmed in a live test on Gemini and BigQuery (2026-10-31). Full research with every source: research/report-questions-db-agent.md. See also the architecture map.

In simple words

  1. One LLM reply can contain several SQL queries. The model sends, for example, 4 run_sql calls in a single answer.[7]
  2. Our code runs them at the same time. LangChain starts all 4 together, and each one becomes its own BigQuery job. They finish in about the time of the slowest one, not the sum.
  3. All 4 results go back to the model together, and it writes the answer or report.

That's 2 LLM calls for the whole report, however many queries the batch holds. If a result raises a new question, the model can send one more round of queries, which makes 3 calls. That's still inside the budget of 5 per question.

The flow

The model plans in its built-in thinking, so it doesn't write the plan as text first. Requiring text right before a tool call can cause a malformed-call error on Gemini 3.x.[7]

Why it's faster: the same 4 queries, two ways

Illustrative timing, using typical durations from the project log on 2026-10-30 (LLM calls 1.5–4.4 s, SQL 1.0–3.3 s). Every extra LLM call also sends the whole conversation to Gemini again, and the free tier limits input tokens per minute as well as requests.[4]

Rule of thumb: send independent queries together, use a second round only when a query needs an earlier result, and compare groups inside one GROUP BY query. Google's agent guidance and Anthropic's tool docs give the same advice: prefer several specific calls, and batch only the calls that don't depend on each other.[8][9][12]

The winning run, step by step (gemini-3.6-flash, batching lines)

Measured, not illustrative. Each BigQuery job ran on its own thread. Gemini accepted LangChain's tool results without call ids on 3.6 Flash, which was an open question in the research.

What the live test showed

  • The batching lines matter. On the same model they turned “limit hit, no report” into a full report in 3 calls. They go into prompts/system.md in step 5.
  • Answer on the last call. When the limit is hit, the user gets nothing useful today. Forcing the last call to answer without tools would have produced a report from the 5 results already gathered.
  • Flash-Lite doesn't batch. It merged everything into one query instead. It still works as a fallback model, but its reports are thinner.
  • 3.6 Flash is slow per call (16–20 s, because it thinks a lot). The time saved comes from BigQuery and from fewer rounds, not from faster LLM calls.
  • Gemini 3.8 Flash was overloaded all day (503), so it's still untested. That's one more reason for the model fallback in step 4.
